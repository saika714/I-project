# 開発ルール

GitHub上の作業の流れは[共同作業ルール](CONTRIBUTING.md)、責務と差し替え契約は[アーキテクチャ](ARCHITECTURE.md)、実装範囲は[マスター仕様](SOFTBALL_GAME_MASTER_SPEC.md)を参照する。

## 環境と作業開始

- Unityは**6000.6.8f1**。ProjectVersion.txt、Packagesのmanifest/lockと同じ環境を使う。個人判断でEditorやパッケージを更新しない。
- 最新の`main`からブランチを作り、Issueで担当と完了条件を共有する。
- 新しい機能は投球→打撃→結果→再挑戦の既存ループを保ちながら小さく追加する。守備・走塁・VRをまとめて着手しない。
- 作業前とコミット前に`git status`を確認する。UnityやIDEが生成した変更を、そのまま全部コミットしない。

## ファイルの配置

| 配置 | ルール |
|---|---|
| Assets/_SoftballConnect/Scripts | 新規C#は責務に対応する層へ置く |
| Assets/_SoftballConnect/Scenes・Prefabs・Config等 | シーン・表示素材・調整値を対応するフォルダへ置く |
| Docs | 仕様・設計・手順・検証・開発ルール。通常の開発文書をAssetsへ置かない |
| .github | GitHubが読み込む案内・PR/Issueテンプレート。開発文書の配置規則の例外 |
| Tools | 開発用スクリプト。実行方法を文書に記載する |
| TestResults | 共有に必要なXML/PNGのみ。変更に関係しない再生成結果をPRに混ぜない |
| プロジェクト直下 | READMEとGit管理ファイルを維持する |

`Library` / `Temp` / `Logs` / IDEキャッシュ / `.csproj` / `.sln`等は生成物として管理対象外。**Assetsの`.meta`、Packagesのmanifest/lock、ProjectSettingsは管理対象**。Git LFSは現在設定していない。大きな素材を追加する場合は先に共有し、必要な運用を決める。

## コードと設定の責務

- DomainとApplicationは`noEngineReferences`を保ち、UnityEngine・Input System・GameObject・UIへ依存させない。
- ゲーム進行と結果確定はGameSessionControllerを入口にする。表示スクリプトから独自に投球・得点・状態遷移を確定しない。
- 入力デバイスはアダプタで`IBatInputSource`へ変換する。判定処理にSpaceキーやXRコントローラーへの直接参照を持ち込まない。
- 表示はシミュレーションの位置・姿勢・状態を受け取る。モデルの見た目を変えるために判定距離や球位置を別管理しない。
- 距離・時間・難易度・素材参照はConfigへ、表示文字列はLocalizationへ置く。共通設定の実行時コピーを使い、プレイ中に元アセットを書き換えない。
- イベント購読は解除する。リトライ・シーン遷移・ポーズで古い状態や購読が残らないようにする。
- 既存のnamespace・命名・4スペースの字下げに合わせる。新規MonoBehaviour/ScriptableObjectはファイル名と公開型名を合わせる。無関係な一括整形はしない。
- バグ修正では再現条件を記録する。判定や状態を変更した場合は、その境界・再発条件を検証する。文言修正にゲームロジックのテストを追加する必要はない。

## Unityアセットの共同編集

### 同じシーン・Prefabの編集を重ねない

シーン、Prefab、共通Config、ProjectSettings、Packagesを編集する前に、Issueへ対象パスと担当者を記載する。チーム内では同じファイルを同時に編集しない運用とする。これはGitやGitHubの自動ロックではない。

```text
編集対象: Assets/_SoftballConnect/Config/DefaultVisualTheme.asset
担当: IssueのAssignee
状態: 編集中 → PRレビュー中 → マージ済み・編集終了
```

他の人が作業中なら、別Prefabやコードなど影響しない箇所を進める。共通シーンに全員の変更を直接詰め込まず、Prefab単位へ分けて最後に配置する。

### .metaとGUIDを保つ

- アセットの移動・改名は原則UnityのProjectウィンドウで行い、`.meta`と一緒に移動する。
- 追加時はアセットと生成された`.meta`を同じコミットへ含める。削除する場合も対応する両方を確認する。
- 既存アセットの`.meta`を消して作り直したり、GUIDを手入力で変更したりしない。参照先が壊れる。
- フォルダ移動は別PRで共有する。参照保持と差分を確認し、機能開発中の大規模移動を避ける。
- Force Textによるテキストシリアライズを維持し、`.meta`を可視ファイルとして管理する。テキスト形式でもシーン競合が自動で安全に解決するとは限らない。

### 競合と保存

Gitの同期・マージ前にシーンを保存してEditorを閉じる。競合は両者の意図を確認して解決し、EditorでMissing Script、Missing参照、塁・球・バットの位置を確認する。判断できないシーン競合は片方の変更をベースに、もう片方の意図をEditorで再適用する。

Play時に生成されるHierarchyはPlay終了後に残らない。永続化する変更はConfig/Prefab/コードへ反映する。調整値が意図せず保存・初期化されていないか差分を確認する。

## 素材・依存の追加

- 表示は打者視点と実寸の球場を基準にし、プレイヤー原点を打球や結果に応じて自動移動しない。基本表示は英語、日本語切り替えを残す。旧アセットに合わせる必要はない。外部素材を追加する場合はライセンスと出典・利用条件を確認し、Issue/PRへ記載する。
- 未確認の旧Floreswa素材は整理済み。新しい素材も出典・利用条件を確認してから採用する。
- 外部SDK・有料素材・新規パッケージ・Unity更新は、目的と影響を事前共有し別PRにする。manifestとlockをセットで更新する。
- APIキー、トークン、パスワード、個人データをコミットしない。必要な設定は共有方法とサンプルだけを文書化する。

## 確認・完了条件

構成の確認はプロジェクト直下で実行する。

```bash
python3 Tools/validate_project.py
git diff --check
```

ゲームに影響する変更はUnityでコンパイルし、影響するテストと操作を確認する。基本の通し確認は、Bootstrap→メニュー→開始→打撃→結果→次球→規定球数終了→再挑戦。必要に応じて見送り・連続入力・ポーズ・R・メニュー復帰・日英切替も確認する。

PRにはEditorバージョン、実行したテスト・手動操作、結果、未実施項目を分けて記載する。テストの成功を目視・実物入力・Standalone・Questの成功へ読み替えない。現在の未検証事項は[検証記録](VALIDATION.md)へ引き継ぐ。
